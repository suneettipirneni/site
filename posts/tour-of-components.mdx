Good technical writing moves between an idea and its details. This page collects the elements I use to make that movement easier to follow.

# Text and hierarchy

A paragraph sets the pace. **Emphasis** draws attention to the important part, while _italics_ leave room for a quieter aside. Links connect an explanation to [another article on this blog](/blog/posts/algebraic-data-types). Inline code, such as `Result<T, Error>`, belongs in the sentence around it.

## A closer look

Section headings describe the next idea. A short subsection should still have enough space to feel distinct from the paragraph before it.

# Lists and definitions

A useful explanation often starts with a short sequence.

1. State the input and the expected result.
2. Work through one concrete example.
   - Include the ordinary case.
   - Check what happens at the boundary.
3. Connect the result to the original question.

A checklist records progress without another paragraph.

- [x] Keep headings descriptive.
- [x] Give examples enough room to breathe.
- [ ] Revisit the explanation after using it in practice.

# Code

A short function can explain a rule more precisely than a paragraph.

```typescript
function double(value: number) {
	return value * 2;
}
```

## Titles and highlighted lines

A filename gives the example context. Highlighted lines show the part worth examining. Line numbers help when referring back to a specific step.

```typescript title="examples/collections/sum-positive-values.ts" {2-4} showLineNumbers
export function sumPositive(values: number[]) {
	return values
		.filter((value) => value > 0)
		.reduce((total, value) => total + value, 0);
}
```

# Notes and disclosures

Extra detail should be available when the reader needs it. Open a note to see how ordinary Markdown works inside a custom component.

<InfoBlock title="Why an example should keep its assumptions close to the code that depends on them">

A note can hold the same elements as the article.

- State the assumption explicitly.
- Show the smallest example that depends on it.

```typescript title="average.ts"
const average = (total: number, count: number) => total / count;
```

Here, the caller must ensure that $count > 0$.

</InfoBlock>

<InfoBlock title="Check the boundary case" kind="warning">

An empty collection changes the problem. Decide what the function should return before relying on the ordinary case.

</InfoBlock>

<InfoBlock title="Do not discard an error silently" kind="danger">

A missing result and a failed computation tell the caller different things. Preserve that distinction in the return type.

</InfoBlock>
